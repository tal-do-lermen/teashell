Concorrência: threads, Arc, Mutex e channels

Rust resolve data races em tempo de compilação. Em Java, synchronized é responsabilidade e disciplina sua; em Rust, o compilador recusa código que compartilha estado de forma insegura. É o famoso "fearless concurrency".

Threads básicas

Java 
Thread t = new Thread(() -> {
    System.out.println("worker");
});
t.start();
t.join();
Rust 
use std::thread;

let handle = thread::spawn(|| {
    println!("worker");
});
handle.join().unwrap();

Detalhe de ownership: a closure passada para a thread precisa possuir o que usa (a thread pode sobreviver ao escopo), por isso o move:

let dados = vec![1, 2, 3];
let handle = thread::spawn(move || {
    println!("{:?}", dados);    // `dados` mudou de dono p/ a thread
});
handle.join().unwrap();
// println!("{:?}", dados);     // ERRO: moved

O problema que o compilador resolve

Em Java, isto compila e às vezes funciona (a pior classe de bug):

Java 
class Contador { int n = 0; }
var c = new Contador();
new Thread(() -> c.n++).start();
new Thread(() -> c.n++).start();
// compila. race condition em produção.
// "funciona na minha máquina"
Rust 
let mut n = 0;
thread::spawn(|| n += 1);   // ERRO:
// closure may outlive... e mesmo
// com move: duas threads exigiriam
// duas movimentações — impossível
// compartilhar sem proteção explícita

Por trás disso estão os marker traits Send (pode ser transferido entre threads) e Sync (pode ser referenciado de várias threads). Você não os implementa — a std os deriva automaticamente para tipos seguros e remove de tipos inseguros. O compilador usa isso para bloquear compartilhamento perigoso.

Arc<Mutex<T>> — o padrão mais comum

Para compartilhar estado mutável entre threads, você declara como compartilha:

use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let contador = Arc::new(Mutex::new(0u64));

    let mut handles = vec![];
    for _ in 0..10 {
        let contador = Arc::clone(&contador);   // +1 no refcount, atômico
        handles.push(thread::spawn(move || {
            let mut n = contador.lock().unwrap(); // trava até obter
            *n += 1;
        }));                                      // lock liberado ao sair do escopo (RAII)
    }
    for h in handles { h.join().unwrap(); }

    println!("{}", *contador.lock().unwrap());    // 10 — sempre
}
RustJava
Arc<T>referência compartilhada gerenciada pelo GC (mas contagem atômica manual aqui)
Mutex<T>synchronized / ReentrantLock — mas o Mutex contém os dados (impossível acessar sem lock)
lock() retorna um guard— liberar é automático ao sair do escopo: esquecer unlock é impossível
RwLock<T>ReentrantReadWriteLock — muitos leitores ou um escritor

A grande diferença conceitual: em Java, qualquer código pode acessar o campo compartilhado e esquecer de sincronizar. Em Rust, os dados estão dentro do Mutex — o único acesso possível é através do lock. A disciplina virou linguagem.

Channels — passagem de mensagens

O lema de Go vale aqui: "não comuniquem estado compartilhando; compartilhem estado comunicando".

use std::sync::mpsc;          // multi-producer, single-consumer
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();     // (transmissor, receptor)

    for id in 0..3 {
        let tx = tx.clone();            // um tx por produtor
        thread::spawn(move || {
            let msg = format!("evento da thread {id}");
            tx.send(msg).unwrap();
        });
    }
    drop(tx);                           // encerra produtor principal

    for recebida in rx {                // itera até o canal fechar
        println!("shell recebeu: {recebida}");
    }
}

Canais são o coração da arquitetura que o shell vai usar: o event loop recebe eventos (Wayland, D-Bus, IPC) e distribui para módulos via canais. Guarde este padrão — a página de arquitetura retoma o assunto.

Onde cada ferramenta brilha no shell

  • Canais (mpsc): event bus — Wayland/D-Bus/IPC publicam, módulos consomem.
  • Arc<RwLock<T>>: configuração e estado compartilhado, lido por muitos, escrito raramente (hot reload).
  • Arc<Mutex<T>>: estado pequeno e mutado com frequência.
  • Threads puros: work dedicado (watch de arquivos, decode de imagem).

Exercícios

  1. Spawne 5 threads que enviam "olá N" por um canal; o main imprime na ordem que chega.
  2. Compartilhe um Vec<String> com Arc<Mutex>; cada thread insere seu nome; o main imprime o resultado final.
  3. Simule um event bus: uma thread produtora gera números, o consumidor soma até receber 0 (use enum Evento { Tick(u32), Fim }).
  4. Refaça o 3 com 3 produtores (dica: tx.clone()).
