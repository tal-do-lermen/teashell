Módulos e visibilidade

Diferente de Java (pacotes = pastas, mágicos), em Rust a árvore de módulos é declarada no código:

// src/main.rs
mod config;          // declara o módulo (carrega src/config.rs)
mod ui;              // carrega src/ui/mod.rs ou src/ui.rs

fn main() {
    let c = config::carregar();      // caminho completo
    ui::bar::render(&c);             // submódulo
}

// src/config.rs
pub fn carregar() -> String {        // `pub` = visível fora do módulo
    String::from("tema=escuro")
}

// src/ui/mod.rs
pub mod bar;          // src/ui/bar.rs
RustJava/JS
mod x;estrutura de pastas decide (Java) / import (JS)
pubpublic
sem marcador (padrão)private — visível só no módulo e filhos
pub(crate)protected/package-private — visível só no crate
use crate::config::carregar;import

Paths especiais: crate:: (raiz do binário/biblioteca, como um import comigo.*), super:: (módulo pai, como ../).

main.rs + lib.rs — a forma idiomática

src/
├── main.rs        # binário: só bootstrap (parse args, init, run)
├── lib.rs         # a "biblioteca" do próprio projeto
├── config.rs
├── state.rs
└── ui/
    ├── mod.rs
    ├── bar.rs
    └── launcher.rs
// main.rs
fn main() {
    if let Err(e) = shell::run() {
        eprintln!("erro fatal: {e:?}");
        std::process::exit(1);
    }
}

// lib.rs
pub mod config;
pub mod state;
pub mod ui;

pub fn run() -> anyhow::Result<()> {
    // montar tudo aqui — testável, pois é biblioteca
    Ok(())
}

Colocar a lógica em lib.rs permite cargo test cobrir tudo, e o binário fica um casca fina. É o padrão de projetos sérios — e o que o shell vai seguir.

Crates e workspaces

  • Crate = unidade de compilação (um binário ou uma biblioteca) publicável no crates.io (≈ pacote npm / artefato Maven).
  • Package = um Cargo.toml com 1+ crates.
  • Workspace = vários packages num repositório, compartilhando target/ e Cargo.lock (≈ npm workspaces / multi-module Maven). 
    shell/
├── Cargo.toml            # [workspace] members = [...]
├── crates/
│   ├── shell-core/       # estado + event bus
│   ├── shell-wayland/    # integração wayland
│   ├── shell-dbus/       # notificações, áudio, rede...
│   └── shell-ui/         # componentes visuais
└── shell/                # binário final

O roadmap do shell vai caminhar para exatamente esta divisão — cada módulo independente, compilando em paralelo, com fronteiras claras.

Logging com tracing

O ecossistema usa a facade log (≈ slf4j) ou tracing, que adiciona spans (contexto estruturado e duração) — ideal para apps de longa duração como o shell:

[dependencies]
tracing = "0.1"
tracing-subscriber = { version = "0.3", features = ["env-filter"] }
fn main() {
    tracing_subscriber::fmt()
        .with_env_filter("info")      // ou RUST_LOG=debug cargo run
        .init();

    let span = tracing::info_span!("carregar_config");
    let _guard = span.enter();

    tracing::info!(tema = "escuro", "config carregada");
    tracing::debug!("detalhes extras aqui");
    tracing::warn!("bateria em 15%");
    tracing::error!("falhou: {e}");
}

Nível por módulo via variável de ambiente: RUST_LOG=shell_ui=debug,info cargo run. Compare com logging.properties do Java — mais simples.

Testes

Java 
// src/test/java/CalcTest.java
class CalcTest {
    @Test
    void soma() {
        assertEquals(4, Calc.soma(2, 2));
    }
}
// mvn test
Rust 
// no PRÓPRIO arquivo (idiomático)
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn soma() {
        assert_eq!(soma(2, 2), 4);
    }
}
// cargo test
  • Testes de unidade vivem junto do código (#[cfg(test)] só compila em teste) — testáveis até de itens privados.
  • Testes de integração ficam em tests/, um arquivo por binário de teste.
  • Macros: assert!, assert_eq!, assert_ne!, #[should_panic].
  • Nada de JUnit: o harness de testes é embutido no cargo.

Projeto final da Parte 1

Junte tudo num mini-shell-clock:

  1. Crate com lib.rs + main.rs, módulos config e loop.
  2. Uma thread produtora envia Evento::Tick a cada segundo por canal.
  3. O main consome o canal num while let, loga com tracing.
  4. Config fake (const ou &str TOML) validada com Result + thiserror.
  5. Erro fatal no boot → anyhow com .context().
  6. 1 teste de unidade, cargo fmt e cargo clippy limpos.

~100 linhas. Se você conseguiu, tem o arsenal da Fase 1 do roadmap — siga para Wayland.
