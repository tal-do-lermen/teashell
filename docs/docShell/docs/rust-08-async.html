Async/await e Tokio

Se você vem do JS, a sintaxe parece familiar — mas o modelo mental é diferente. Se vem do Java, pense em CompletableFuture com sintaxe bonita e um scheduler de verdade.

Async não é thread — é estado suspendível

async fn não executa nada quando chamada. Ela retorna um future — um estado de máquina que só avança quando alguém o awaita (ou o runtime o "polla").

JavaScript 
async function carregar() {
  const r = await fetch(url);
  return r.text();
}
carregar();  // JÁ começa a executar
             // (promises são eager)
Rust 
async fn carregar() -> String {
    let r = fazer_request(url).await;
    r.texto().await
}
// carregar() NÃO faz nada ainda —
// futures são lazy
let texto = carregar().await;  // agora sim

Duas diferenças estruturais do JS: (1) futures são lazy — nada acontece até o .await; (2) Rust não tem runtime embutido — o event loop é uma biblioteca, e a padrão do ecossistema é o Tokio. Em JS o runtime é o navegador/node; em Rust você escolhe e declara.

Tokio — o runtime padrão

[dependencies]
tokio = { version = "1", features = ["full"] }
#[tokio::main]              // transforma main no runtime async
async fn main() {
    tokio::time::sleep(std::time::Duration::from_secs(1)).await;
    println!("1 segundo depois");
}

O pecado capital do async: bloquear a thread do runtime. Nunca use std::thread::sleep, I/O bloqueante pesado ou loops longos dentro de código async — trava as outras tarefas. Para trabalho bloqueante: tokio::task::spawn_blocking(...). Para dormir: tokio::time::sleep.

Concorrência: a tabela de tradução do JS

JavaScriptTokio (Rust)Observação
Promise.all([a, b])tokio::join!(a, b)roda em concorrência, espera ambas
Promise.race([a, b])tokio::select! { ... }primeira que termina vence
chamar async functiontokio::spawn(futuro)roda "em background" na multitarefa do runtime
await.awaitsuspende a tarefa, não a thread
use tokio::time::{sleep, Duration};

#[tokio::main]
async fn main() {
    // join!: duas tarefas em paralelo
    let (a, b) = tokio::join!(
        async { sleep(Duration::from_millis(100)).await; "a" },
        async { sleep(Duration::from_millis(50)).await; "b" },
    );
    println!("{a} {b}");   // levou ~100ms, não 150

    // select!: corrida com timeout
    tokio::select! {
        v = trabalhar() => println!("pronto: {v}"),
        _ = sleep(Duration::from_secs(2)) => println!("timeout"),
    }
}

Diferenças do spawn de threads: tokio::spawn é baratíssimo (milhares de tarefas), mas o future precisa viver o suficiente — na prática, dados enviados pra task usam move e, quando compartilhados, Arc (o mesmo capítulo anterior; async não substitui concorrência, complementa).

Canais async

O padrão event bus, agora não-bloqueante (o consumidor .await em vez de travar a thread):

use tokio::sync::mpsc;

enum Evento {
    Tick,
    Tecla(String),
    Sair,
}

#[tokio::main]
async fn main() {
    let (tx, mut rx) = mpsc::channel(64);   // canal com buffer

    let produtor = tokio::spawn(async move {
        for _ in 0..5 {
            tx.send(Evento::Tick).await.unwrap();
        }
        tx.send(Evento::Sair).await.unwrap();
    });

    while let Some(evento) = rx.recv().await {   // o event loop!
        match evento {
            Evento::Tick => println!("tick"),
            Evento::Tecla(k) => println!("tecla: {k}"),
            Evento::Sair => break,
        }
    }
    produtor.await.unwrap();
}

Este while let Some(ev) = rx.recv().await é, em miniatura, o formato do loop principal do shell: esperar eventos, despachar por tipo, decidir se renderiza. A página de arquitetura expande exatamente este esqueleto.

Estado compartilhado async

  • Arc<tokio::sync::Mutex<T>> — o Mutex do Tokio pode ser travado através de pontos .await (o de std não; travado sobre await = risco de deadlock com o runtime).
  • Regra prática: std::sync::Mutex para seções curtas sem await dentro; tokio::sync::Mutex quando precisa segurar o lock além de um .await.

Async no projeto do shell

  • D-Bus via zbus: API async nativa — signals chegam como streams.
  • IPC (unix socket): tokio::net::UnixListener.
  • Wayland: o wayland-client tem seu próprio event queue; há integração async, mas o loop de frames ficará no lado síncrono — híbrido comum em shells reais.
  • Use async onde há I/O de serviços; threads onde há CPU/codec/render. Não seja "async everywhere" por moda.

Exercícios

  1. Converta um exemplo seu de Promise.all para tokio::join! e cronometre com std::time::Instant.
  2. Faça uma "corrida": duas tasks dormem tempos diferentes; select! imprime a vencedora.
  3. Implemente timeout: select! entre uma task lenta e sleep(2s).
  4. Adapte o exemplo do event bus: produtor envia Tecla aleatórias e Sair após 5 eventos.
