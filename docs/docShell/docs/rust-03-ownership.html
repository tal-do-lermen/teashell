Ownership, borrowing e lifetimes

O capítulo que mais diferencia Rust de Java/JS. Em vez de um garbage collector, o compilador gerencia a memória em tempo de compilação. Dominar isto = 80% da curva de aprendizado.

O problema que ownership resolve

Em Java/JS, o GC varre o heap periodicamente e libera o que ninguém referencia. Funciona, mas tem custo: pausas, overhead de memória, e nenhuma previsibilidade sobre quando a memória é liberada.

Rust troca o GC por três regras verificadas em tempo de compilação (zero custo em runtime):

  1. Cada valor tem um dono (owner) — a variável que o possui.
  2. Só pode existir um dono por vez.
  3. Quando o dono sai de escopo, o valor é descartado (memória liberada na hora, sem GC).

Move semantics

O que acontece quando você "atribui" uma variável que vive no heap?

Java 
String a = "oi";
String b = a;
// duas referências para o MESMO objeto
// o GC cuida de tudo
System.out.println(a);  // "oi"
Rust 
let a = String::from("oi");
let b = a;
// a propriedade foi MOVIDA para b
// `a` não existe mais
println!("{a}");  // ERRO: borrow of moved value

Isso não é uma cópia — é uma mudança de dono. Nada é liberado duas vezes, nada vaza: o compilador simplesmente proíbe usar a variável antiga.

Tipos simples (i32, f64, bool, char, tuplas deles) são Copy: atribuição copia o valor e a original continua válida, como você espera de int em Java. A regra do move vale para tipos compostos (String, Vec, structs…).

Borrowing: referências

Mover tudo seria inviável. Para usar um valor sem assumir a posse, emprestamos com &:

fn tamanho(s: &String) -> usize {   // recebe emprestado, não possui
    s.len()
}

fn main() {
    let s = String::from("hello");
    let n = tamanho(&s);            // empresta…
    println!("{s} tem {n} chars");   // …e `s` continua válida
}

Há dois tipos de empréstimo, com uma regra de ouro:

EmpréstimoRegraAnalogia
&T (compartilhada)Quantas quiser simultaneamente, mas todos só leemlock de leitura
&mut T (exclusiva)Uma só por vez, e nenhuma & juntolock de escrita
let mut v = vec![1, 2, 3];

let a = &v;          // ok
let b = &v;          // ok: vários leitores
println!("{a:?} {b:?}");

let m = &mut v;      // ok: leitores anteriores já encerraram
m.push(4);           // exclusivo: muta
// let x = &v;       // ERRO se `m` ainda for usada depois

É exatamente o modelo de ReentrantReadWriteLock de Java — mas verificado em tempo de compilação, sem custo em runtime. Data races e mutação concorrente acidental ficam impossíveis na linguagem, não na disciplina do programador.

Slices

Referência para uma fatia de uma coleção — você já usou sem notar: &str é um slice de string.

let s = String::from("desktop shell");
let palavra: &str = &s[0..7];    // "desktop"
let resto: &str = &s[8..];       // "shell"

let nums = [10, 20, 30, 40];
let fatia: &[i32] = &nums[1..3]; // [20, 30]

Lifetimes (sem pânico)

Lifetime é o intervalo em que uma referência é válida. O compilador já verifica todos automaticamente; as anotações ('a) só aparecem quando ele precisa de ajuda para relacionar lifetimes de entradas e saídas:

// "a retorno vive tanto quanto a MENOR vida entre a e b"
fn mais_longa<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}
  • Anotar não muda nada em runtime — é só uma assinatura de contrato, como genéricos.
  • A maioria dos casos é inferida (elision): fn primeira(s: &str) -> &str não precisa de anotação.
  • 'static = vive o programa inteiro (literais, dados globais).

Como iniciante você raramente escreverá lifetimes. Quando precisar, o compilador sugere a anotação exata. Não tente "decorar" — aprenda-os quando um erro real aparecer.

Erros clássicos do borrow checker

Código que não compilaPor quêComo resolver
let mut v = vec![1];
let r = &v[0];
v.push(2);        // muta…
println!("{r}");  // …enquanto r vive
 mutação com referência ativa terminar o uso de r antes de mutar, ou reordenar o código 
let mut x = 5;
let a = &mut x;
let b = &mut x;
println!("{a} {b}");
 duas referências mutáveis ao mesmo tempo usar cada &mut em escopos separados 
fn dangle() -> &String {
    let s = String::from("x");
    &s            // s morre aqui
}
 retornar referência a dado local retornar String (o dono), não &String

Checklist mental

  • Atribuição de tipo composto move; depois do move, a origem é inválida.
  • Para só usar (ler), passe &valor; para alterar, &mut valor e o parâmetro como &mut T.
  • Muitos & ou um &mut — nunca os dois juntos.
  • Referência não pode sobreviver ao dono dos dados.
  • Erro de borrow checker não é punição: é o design do seu programa sendo auditado de graça.

Exercícios

  1. Escreva fn maior(v: &Vec<i32>) -> i32 e chame-a mantendo o vetor utilizável depois.
  2. Escreva fn dobrar_todos(v: &mut Vec<i32>) que muta o vetor in place.
  3. Deixe este código compilar — sem clonar nada: let s = String::from("abc"); let t = s; println!("{s} {t}");
  4. Faça fn primeira_palavra(s: &str) -> &str (dica: s.split(' ').next() ou find(' ')).
