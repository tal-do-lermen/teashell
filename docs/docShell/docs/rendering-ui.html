UI Toolkit

Antes de escolher uma biblioteca, entenda os conceitos:

  • Widget tree
  • Layout engine
  • Retained mode
  • Immediate mode
  • Hit testing
  • Focus management
  • Keyboard navigation
  • Mouse/pointer events
  • State management
  • Reactive UI
  • Rendering pipeline

Retained vs immediate: em retained mode (Iced, Slint, como JavaFX/React) existe uma árvore de widgets persistente que você atualiza; o framework decide quando redesenhar. Em immediate mode (egui, como Dear ImGui) você descreve a UI inteira todo frame e a biblioteca diffifica por baixo. Vale conhecer os dois modelos antes de escolher.

Exemplo 3 — input: pointer até o hit testing

// Cargo.toml: wayland-client = "0.31"
use wayland_client::{
    protocol::{wl_pointer, wl_seat},
    Connection, Dispatch, QueueHandle, WEnum,
};

struct App {
    cursor: (f64, f64),
    hover: Option<wayland_client::protocol::wl_surface::WlSurface>,
    // ...
}

// o compositor anuncia o que o seat tem (mouse? teclado?)
impl Dispatch<wl_seat::WlSeat, ()> for App {
    fn event(state: &mut Self, seat: &wl_seat::WlSeat, event: wl_seat::Event,
             _: &(), _: &Connection, qh: &QueueHandle<Self>) {
        if let wl_seat::Event::Capabilities { capabilities: WEnum::Value(caps) } = event {
            if caps.contains(wl_seat::Capability::Pointer) {
                let _pointer = seat.get_pointer(qh, ());    // cria o proxy do mouse
            }
            if caps.contains(wl_seat::Capability::Keyboard) {
                let _keyboard = seat.get_keyboard(qh, ());
            }
        }
    }
}

// os eventos do mouse chegam aqui — em COORDENADAS DA SUA SURFACE
impl Dispatch<wl_pointer::WlPointer, ()> for App {
    fn event(state: &mut Self, _p: &wl_pointer::WlPointer, event: wl_pointer::Event,
             _: &(), _: &Connection, _qh: &QueueHandle<Self>) {
        match event {
            wl_pointer::Event::Enter { surface, surface_x, surface_y, .. } => {
                state.hover = Some(surface);
                state.cursor = (surface_x, surface_y);
            }
            wl_pointer::Event::Motion { surface_x, surface_y, .. } => {
                state.cursor = (surface_x, surface_y);      // f64, lógico
            }
            wl_pointer::Event::Button { button, state: WEnum::Value(botao), .. } => {
                if botao == wl_pointer::ButtonState::Pressed {
                    // hit testing: qual widget está em state.cursor?
                    state.click(button);
                }
            }
            wl_pointer::Event::Leave { .. } => state.hover = None,
            _ => {}   // frame, axis (scroll), axis_source...
        }
    }
}
  • O campo button é um código bruto do kernel (0x110 = botão esquerdo) — vem de linux/input-event-codes.h.
  • Teclado segue o mesmo padrão: wl_keyboard entrega Keymap, Modifiers, Key (código bruto + keymap xkb para traduzir).
  • Na arquitetura do shell, cada um desses branches vira um Evento enviado ao bus (Exemplo 5).
  • eventos de wl_pointer na spec — a lista completa com semântica de cada um
  • docs.rs/wayland-client — módulos wl_pointer/wl_keyboard
  • Para o cursor visual: protocolo wp_cursor_shape_manager_v1 (o compositor desenha o cursor pra você) — docs.rs/wayland-protocols

Exemplo 4 — o frame com wgpu (esqueleto)

// Cargo.toml: wgpu = "25"   // confira a versão atual — a API muda entre majors

fn render(device: &wgpu::Device, queue: &wgpu::Queue, surface: &wgpu::Surface) {
    // pega o próximo buffer — BLOQUEIA até o vsync/frame callback do compositor
    let frame = surface.get_current_texture().unwrap();
    let view = frame.texture.create_view(&Default::default());

    let mut encoder = device.create_command_encoder(&Default::default());
    {
        let mut pass = encoder.begin_render_pass(&wgpu::RenderPassDescriptor {
            color_attachments: &[Some(wgpu::RenderPassColorAttachment {
                view: &view,
                resolve_target: None,
                ops: wgpu::Operations {
                    load: wgpu::LoadOp::Clear(wgpu::Color {   // "pinta o fundo"
                        r: 0.06, g: 0.09, b: 0.12, a: 1.0,
                    }),
                    store: wgpu::StoreOp::Store,
                },
            })],
            ..Default::default()
        });
        // aqui dentro vão os draw calls dos seus widgets
    }
    queue.submit([encoder.finish()]);
    frame.present();
}

get_current_texture() já implementa o frame pacing: ele espera o momento certo do refresh — é o frame callback do protocolo virando código. A parte que conecta a Wayland surface ao wgpu (EGL/handles) é a mais chata de escrever na mão: não reinvente, copie de um exemplo oficial.
